# 7. Internet 6.00 in 750 lines

The guest half of HostNet is one C file, one short assembly file and a list of SWI
names. This chapter walks through it from build to shutdown: how it is built and why
not with the usual RISC OS tools, how it finds the doorbell, the one keyword without
which every request appeared to fail, the transport and the wait loop, how errors are
returned, why it refuses to load on a machine without the doorbell, and the two ways
it gets into a running machine.


<!-- doccrate:keep-together:start -->

## What the module says it is

The header comment of `riscos-pi4/hostnet/hostnet.c` sets out the whole job:

```c
/*
 * HostNet — the guest half.  Internet 6.00.
 *
 * It claims the Internet module's name and its SWI chunk (&41200), and
 * every one of the thirty-five socket SWIs does the same thing: copy R0-R7
 * into a request block, ring the doorbell at the GENET window, copy R0
 * back.  It does not interpret the registers, does not know what a socket
 * is, and holds no state beyond the block itself.  All the networking is
 * on the host (hw/misc/hostnet.c).
 ...
 */
```

### Identity

| Item | Value |
|:---|:---|
| title | `Internet` |
| help string | `HostNet 6.00 (14 Sep 2026)` |
| SWI chunk and prefix | &41200, `Socket` |
| SWIs | 35, generated from `swis.txt` |
| star commands | `*HostNetPing`, `*HostNetInfo` |
| entry points | `hostnet_init`, `hostnet_final`; no service call handler |

<!-- doccrate:keep-together:end -->


Where the ROM's Internet module is also present, the kernel gives the *later* claimant
of a SWI chunk priority, so HostNet would win anyway. The comment is clear that this is
"not the plan, it is the safety net". The plan is that the ROM's stack is not running:
unplugged in CMOS when HostNet is spliced into the ROM, or replaced as HostNet loads
from the disc.

## Building it

`build-hostnet.sh` uses the same toolchain as the HostFS module beside it: ROSCC's
module header generator and linker, clang targeting ARM, and ROSCC's small runtime.
It is not built with the RISC OS Desktop Development Environment. The script's
comment gives the reason: the module has to be able to run from ROM, and the usual
module header generator and C library stubs both write into the module image during
initialisation, which in ROM is a data abort.


<!-- doccrate:keep-together:start -->

### The build, step by step

| Step | Tool | Output |
|:---|:---|:---|
| 1. the SWI list | a short Python script over `swis.txt` | the C entry points and the header's SWI list |
| 2. the module header | ROSCC's `gen_module.py` | `module_head.s` |
| 3. the code | clang: the header, `hostnet_entries.s`, `hostnet.c` | object files |
| 4. the runtime | clang: ROSCC's runtime sources | object files |
| 5. the link | `roscc link --module` | `build/HostNet,ffa` |

#### Generating the entry points

Step 1 is what keeps the SWI order right. The same list produces both the module
header's table of names and the C entry points, so the two cannot disagree:

```python
names = [n for n in open('swis.txt').read().split() if n]
nl = chr(10)
open('hostnet_swis.inc', 'w').write(
    '/* Generated by build-hostnet.sh from swis.txt -- do not edit.' + nl +
    ' * One entry point per socket SWI, in chunk order from &41200.' + nl +
    ' * Each is a veneer target: it does nothing but name its own number. */'
    + nl +
    nl.join(f'HN_ENTRY({i:02d}, {i})  /* Socket_{n} */'
            for i, n in enumerate(names)) + nl)
```

<!-- doccrate:keep-together:end -->


Each generated line expands, through the `HN_ENTRY` macro at the end of `hostnet.c`,
into a function that calls `hn_call` with its own number.

### The compiler flags

| Flag | Why |
|:---|:---|
| `--target=armv8a-none-eabi -mcpu=cortex-a72` | the emulated processor, in 32-bit mode |
| `-ffreestanding -nostdlib -fno-builtin` | a module has no C library but the runtime linked in |
| `-fropi -frwpi` | position-independent code and data, found through R9 |

The heap comment finishes the thought: "every request goes in one static block, and
every buffer it touches belongs to the caller." A local build of the module, made on

## Finding the doorbell

The first version of the module used the doorbell's physical address as if it were a
logical one, and took a data abort during boot "with nothing on screen to say why".
RISC OS maps peripherals into logical memory on request, so the address must come
from `OS_Memory 13`, which maps a physical range permanently and returns where it now
lives:

```c
static volatile uint32_t *os_map_io(uint32_t phys, uint32_t size)
{
    register uint32_t r0 __asm("r0") = 13;
    register uint32_t r1 __asm("r1") = phys;
    register uint32_t r2 __asm("r2") = size;
    register uint32_t r3 __asm("r3");
    register uint32_t v __asm("r4");

    __asm volatile("swi 0x20068\n\tmrs r4, cpsr"
                   : "+r"(r0), "+r"(r1), "+r"(r2), "=r"(r3), "=r"(v)
                   :
                   : "r12", "lr", "cc", "memory");
    if (v & (1u << 28)) {
        return 0;
    }
    return (volatile uint32_t *)r3;
}
```

<!-- doccrate:keep-together:end -->


This is how every SWI in the module is made, with the same register-binding assembly
form that ROSCC's runtime uses. The string holds the instructions; the lists after it
bind the C register variables and name what the call may overwrite. SWI &20068 is
the error-returning form of `OS_Memory`. The `mrs` after it copies the flags into R4,
and bit 28 is V, set on an error.

The Sprint 0 commit adds a second trap: `OS_ValidateAddress` "happily calls the fixed
address valid and the load still takes a data abort". A validity check is no
substitute for asking the operating system to map the page.

## The block that had to be `volatile`

The request block is a static array of 16 words, and its declaration carries a
comment that is worth reading in full:

```c
/*
 * volatile, and not as a formality: the host writes into this block
 * through the guest's MMU while the compiler believes nothing can have
 * touched it.  Without it, an optimising build folds the read of the
 * result back to the poison value written a line earlier and every
 * request appears to fail.  (HostFS avoids this only by building at -O0.)
 */
static volatile uint32_t req[H_WORDS] __attribute__((aligned(16)));
```

<!-- doccrate:keep-together:end -->


<!-- doccrate:keep-together:start -->

### What the optimiser saw

| Source line | What the compiler knows without `volatile` | What really happens |
|:---|:---|:---|
| `req[H_RC] = 0xFFFFFFFFu;` | `req[H_RC]` now holds 0xFFFFFFFF | the same |
| `hn_reg(HN_CMD / 4) = (uint32_t)req;` | a write that stores `req`'s address and changes nothing in it | the host runs the request and rewrites `req[H_RC]` |
| `return req[H_RC];` | still 0xFFFFFFFF, so return the constant | the host's answer, if the compiler reads memory |

<!-- doccrate:keep-together:end -->


Without `volatile`, the compiler is entitled to skip the read and return 0xFFFFFFFF.
Every request then looks unanswered. The keyword tells it that the memory can change
behind its back, which is exactly the case.


<!-- doccrate:keep-together:start -->

## The transport

Two small functions ring the doorbell. `hn_go` stamps the sequence number and the
poison value, and writes the block's address:

```c
static uint32_t hn_go(void)
{
    req[H_SEQ] = ++seq;
    req[H_RC] = 0xFFFFFFFFu;        /* poison: an unanswered request shows */
    hn_reg(HN_CMD / 4) = (uint32_t)req;
    return req[H_RC];
}
```

<!-- doccrate:keep-together:end -->


<!-- doccrate:keep-together:start -->

#### One SWI into the block

`hn_ring_once` fills the header for one SWI and calls it:

```c
static uint32_t hn_ring_once(uint32_t swi, unsigned *regs)
{
    uint32_t i;

    req[H_CMD] = HN_CMD_SWI;
    req[H_SWI] = swi;
    req[H_ERRNO] = 0;
    req[H_RESULT] = 0;
    for (i = 0; i < 8; i++) {
        req[H_REGS + i] = regs[i];
    }
    return hn_go();
}
```

<!-- doccrate:keep-together:end -->


Only R0 to R7 cross, which covers every argument any socket call takes. On the way
back only R0 is written, because R0 is the only register the Internet module ever
returns a value in.


<!-- doccrate:keep-together:start -->

## The wait

`hn_wait_ring` is where a blocking socket call waits. Chapter 4 explained why the host
cannot:

```c
static _kernel_oserror *hn_wait_ring(uint32_t swi, unsigned *regs,
                                     uint32_t *rc_out)
{
    for (;;) {
        uint32_t rc = hn_ring_once(swi, regs);

        if (rc != HN_RC_RETRY) {
            *rc_out = rc;
            return 0;
        }
        if (os_escape()) {
            return sock_error(4);          /* EINTR */
        }
        os_yield();
    }
}
```

<!-- doccrate:keep-together:end -->


`os_yield` makes `OS_UpCall 6` with a pollword that never changes, which is what the
Internet module's own sleep does. A TaskWindow claims the upcall, lets the desktop run,
and returns; with nothing to claim it, the call returns at once. The comment says what
the loop must never do: "spin *without* offering, which would stop a TaskWindow
multitasking at all." `OS_UpCall 6` was added in Sprint 2.


<!-- doccrate:keep-together:start -->

#### From the answer to a result

`hn_call`, which every SWI entry point reaches, puts it together. It returns an error
if the doorbell was never found, sends `Select` to its own loop (chapter 4), runs the
wait, and turns the transport code and errno into a RISC OS result:

```c
    switch (rc) {
    case HN_RC_OK:
        break;
    case HN_RC_NOSOCKETS:
        return &err_nosock;
    case HN_RC_BADSWI:
        return &err_badswi;
    case HN_RC_BADADDR:
        return &err_badaddr;
    default:
        return &err_nodev;
    }

    if (req[H_ERRNO]) {
        return sock_error(req[H_ERRNO]);
    }
    regs[0] = req[H_RESULT];
    return 0;
```

<!-- doccrate:keep-together:end -->


## Errors

A socket error goes back the way the Internet module sends it: an error block numbered
&20E00 plus the errno, with the errno's name as the message. The blocks are kept in a
ring of four and used in turn, as the Internet module does. That protects a program
that has not yet copied one error from a second error, raised by a callback as the SWI
returns, overwriting it.


<!-- doccrate:keep-together:start -->

### The module's own errors

Transport failures are not socket errors, so they use a different number, 0x1E4:

| Message | When |
|:---|:---|
| "Internet: no HostNet device" | the doorbell was never found, or an unexpected transport code |
| "Internet: host serves no sockets" | `HN_RC_NOSOCKETS`: the device is there, sockets are off |
| "Internet: bad socket SWI" | `HN_RC_BADSWI` |
| "Internet: bad address" | `HN_RC_BADADDR`: a pointer in the call would not translate |
| "Internet: HostNet needs the emulator" | returned by initialisation, so the module does not load |
| "HostNet: no answer" | `*HostNetPing` got no magic number back |

<!-- doccrate:keep-together:end -->

## Refusing to exist

Sprint 0's module loaded even where there was no doorbell, and then refused every
call. `3c523600ea` changed that, and its comment explains why a dormant module is
worse than none:

```c
/*
 * Refuse to start unless the doorbell is actually there.
 *
 * This matters more than the usual "stay dormant" politeness, because this
 * module is called Internet and claims the Internet module's SWI chunk.
 * A module that loads and then refuses every call does not sit quietly out
 * of the way -- it shadows the real Internet module, and the kernel gives
 * the later claimant of an in-use chunk priority (Kernel/s/ModHand).  On a
 * real Raspberry Pi that would mean a machine with networking hardware,
 * a working stack in ROM, and nothing able to reach it.
 ...
 */
```

#### `hostnet_init`

The initialisation that follows the comment maps the page and checks it twice:

```c
int hostnet_init(void *ws)
{
    (void)ws;
    live = 0;
    cb_pending = 0;

    hn_base = os_map_io(HN_PHYS, HN_PAGE);
    if (!hn_base || hn_reg(HN_MAGIC / 4) != HN_MAGIC_VALUE) {
        /* No doorbell: this is not our emulator.  Do not load. */
        return (int)&err_notemul;
    }
    if (!(hn_reg(HN_FEATURES / 4) & HN_FEATURE_SOCKETS)) {
        /* The emulator is ours but sockets were not asked for.  Same
         * answer: better no Internet module than a deaf one. */
        return (int)&err_notemul;
    }
    live = 1;
    ...
    os_call_every(HN_TICK_CS, (uint32_t)hostnet_tick, static_base());
    ...
    os_service_internetstatus();
    return 0;
}
```

<!-- doccrate:keep-together:end -->


Returning an error block from initialisation makes the kernel refuse to load the
module, which leaves SWI chunk &41200 unclaimed and a real Internet module, if there
is one, in charge. The commit verified both ways. With the doorbell on,
`*HostNetInfo` reported it live and `*GetHost` resolved. With it off, `*Modules`
listed 138 modules, HostFS among them, no Internet module at all, and the machine
still reached a clean desktop.

After registering the ticker, `hostnet_init` sends `Service_InternetStatus` with the
AddressChanged reason, once, so that a program loaded later that waits for a working
stack is not left waiting for ever. It does not send the InterfaceUpDown reason,
which needs a description of an interface, and there is no interface to describe.

`hostnet_final` removes the ticker before anything else. Its comment says why: "a
ticker pointing into a module that is about to be unplugged is a branch into free
memory."

## Into the machine: two routes


<!-- doccrate:keep-together:start -->

### Spliced into the ROM, or loaded from the disc

| | ROM splice | Load from the disc |
|:---|:---|:---|
| **how** | `rom.py` adds `HostNet,ffa` to the ROM image after HostFS, cached by content | `!Boot`'s `PreDesk.HostModules` loads every module in `HostFS:$.Modules` |
| **the ROM's stack** | Internet, EtherGENET, EtherUSB and DHCP unplugged in CMOS (98, 106, 107, 108) | still in the ROM; the kernel kills its Internet module as HostNet loads |
| **the network card** | none attached | attached, unused while HostNet runs |
| **used by** | `run.py --hostnet`, for development | the Windows release |

<!-- doccrate:keep-together:end -->


Both routes keep MbufManager, chain 97, which looks pointless with no stack to buffer
for. The `rom.py` comment gives the reason. `!Internet`'s start-up checks for
MbufManager and loads it from the disc if it is missing, and the only copy on the disc
is a 26-bit module that cannot load on this machine. The start-up then stops with an
error before running the file that sets the name servers. The machine reaches the
desktop looking healthy, and NetSurf reports that no name servers are configured.
Left in the ROM, MbufManager satisfies the check and allocates nothing.

Both routes share one hazard, which chapter 8 deals with. If HostNet loads while the
doorbell is dark, the ROM's Internet module has already been unplugged or killed,
HostNet declines, and the machine has no Internet module at all.
